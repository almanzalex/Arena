# Arena 1.0 release program

Status: local `1.0.0rc1` implementation complete; the `v1.0.0` tag remains
blocked on the external and release-commit evidence gates in this document.
The latest local proof is [1.0-rc-local-evidence.md](1.0-rc-local-evidence.md).

Arena 0.5 already has the right product shape: a local-first protocol and tooling
layer for reproducible RL artifacts, task runtimes, evaluation providers, stores,
and handoff. Version 1.0 is **claim closure**, not another feature expansion.
The work is to freeze what “compatible” means, make every write and external
boundary fail safely, publish an installable release, and attach reproducible
evidence to every stable claim.

The RC implementation has strict identity and parsing, transaction-safe
publication, supervised hard budgets, structured diagnostics, installable
support/schema registries, signed release evidence, hardened external boundaries,
and executable value flows. Fast, venv-hermetic, and Docker-network-isolated
tests pass locally. Those results are not substitutes for release-commit CI,
public distribution, live external qualifications, multi-platform performance,
the seven-day bake, or independent-user evidence.

## What already exists

- Trainer and lifecycle registries, two distinct offline trainer cases,
  deterministic dataset splits, and exact checkpoint resume.
- Dynamic-agent removal/reentry with ordered segment history and stable-role
  assignment.
- OpenSpiel sequential, chance/imperfect-information, and simultaneous families
  with qualified frozen games.
- OpenEnv task import/equivalence for two typed tasks and Gimitest subprocess
  lineage.
- Concurrent evaluation cells with deterministic output order.
- `file://`, HF, OCI, W&B, and MLflow adapters behind one store-qualification
  format, plus detached Ed25519 attestations.
- Wheel/sdist build, hermetic tests, composed user journey, extensive adversarial
  unit coverage, and milestone evidence documents through 0.5.

The plan reuses these surfaces. It does not replace the registries, artifact
formats, or local-first architecture.

## 1.0 outcome

The primary 1.0 user is a research-infrastructure engineer or lab collaborator
who must transfer a policy and its evaluation claim between repositories,
machines, and execution boundaries without trusting an informal bundle of code.

An independent producer and consumer can install Arena from the public Python
index, exchange the same policy and evaluation artifacts through supported task
runtimes, providers, and stores, verify identity and semantics, reproduce the
declared result within its tolerance, and diagnose or recover from failure without
reading Arena source code.

The release is successful only if all of the following are true:

1. Artifact identity is stable and old promised artifacts remain readable.
2. Native and external executions either verify as equivalent or fail with a
   precise, stable diagnostic.
3. Interrupted operations never leave output that can be mistaken for valid.
4. A clean machine can install, execute, verify, and hand off from published
   artifacts and documentation alone.
5. Every stable external claim has fresh qualification evidence; unavailable
   integrations are labeled preview, not simulated into passing.
6. Release evidence is machine-checkable and bound to the exact tag and artifacts.

## Dream-state delta

| 0.5 today | 1.0 required delta |
|---|---|
| Strong local implementation and simulated qualifications | Public exact-artifact release with live, durable, signed evidence |
| Historical schemas with identity-bearing `v0alpha1` names | Frozen legacy identity plus explicit v1 semantic/binding schemas |
| Concurrent trusted threads | Supervised hard-budget process path and explicit incomplete/failed states |
| Several producers use different write patterns | One publication protocol covering every final output/ref/object |
| Human-only broad CLI errors | Stable JSON/human diagnostics, exit classes, doctor, and exact repairs |
| Docs assume checkout/generated inputs | Packaged three-command demo and measured cross-machine handoff |
| Entry-point loader exists but is not normal discovery | Lazy v1 plugin protocol proven by an out-of-tree wheel |
| External capability breadth | Minimum stable OpenEnv/Gimitest/HF value floor; optional breadth stays preview |

## Product boundary

### Stable 1.0 surface

- Content-addressed policy, match, trajectory, run, population, evaluation,
  dataset, task, trace, mirror, attestation, and qualification artifacts.
- Native task execution and the specifically qualified OpenEnv and OpenSpiel
  adapter cases.
- Built-in evaluation plus specifically qualified external eval providers.
- `file://` stores and each credentialed backend with current live evidence.
- Offline categorical reference trainers and the exact-resume contract.
- Linux and macOS on the Python versions and architectures named in the support
  matrix.

### Preview surface

A registry entry or adapter can ship as preview when its offline contract tests
pass but fresh live qualification is unavailable. Preview is useful, documented,
and fail-loud, but it is excluded from the 1.0 stable claim. A backend moves to
stable by attaching evidence; core code does not need to change.

### NOT in scope

- Hosted accounts, credentials, billing, dashboards, catalogs, or a control plane.
- A universal distributed or online RL trainer, arbitrary optimizer graphs, replay
  services, or environment collection infrastructure.
- Every OpenSpiel game; qualification remains per game ID and semantic family.
- A malware sandbox for untrusted Python, certificate authority, key revocation,
  transparency log, or hardware-key lifecycle.
- Streaming/object-store-native datasets, compression, or very-large-corpus
  orchestration.
- Bit-identical numerics across arbitrary accelerators or dependency versions.
- Windows in 1.0 unless a later plan revision adds a real CI and handoff owner.

These boundaries keep Arena a protocol-and-tooling product. Generality comes through
registries, qualification contracts, and evidence, not a growing hosted platform.

## Claim and support contract

Every named capability has one of three labels:

| Label | Meaning | Required evidence |
|---|---|---|
| `stable` | Included in the 1.0 compatibility promise | Contract tests, release-platform CI, hermetic handoff, and current live qualification when an external service is involved |
| `preview` | Usable, versioned, and fail-loud, but not covered by the stable compatibility promise | Offline contract tests and explicit limitations |
| `unsupported` | Not tested or intentionally outside the product | An actionable refusal instead of best-effort execution |

Initial reference-platform target:

| Platform | 1.0 target | Decision |
|---|---|---|
| Linux x86_64, Python 3.12 and 3.13 | Stable | Required |
| macOS arm64, Python 3.12 and 3.13 | Stable | Required |
| Linux arm64 | Unqualified | Do not imply support from pure-Python source compatibility |
| macOS x86_64 | Unqualified | No maintained runner is attached |
| Windows | Unsupported | Refuse no workflows solely by OS, but make no release claim |

The exact matrix is capability × OS/architecture × Python, not a single global
row. It must live in one machine-readable source and render into the README and
release notes so prose cannot drift from CI. The initial package metadata is
`>=3.12,<3.14`; Python 3.14 support requires its own qualification. CI asserts the
actual architecture, uses pinned runner generations, and covers both the
minimum-supported and latest-resolvable dependency sets.

The minimum external-value floor for `v1.0.0` is non-negotiable:

- native execution and `file://` remain the offline foundation;
- one separately deployed OpenEnv task runtime is stable;
- Gimitest executes a non-no-op scenario through a genuinely separate interpreter
  and is stable;
- Hugging Face is the required stable remote-store round trip.

OCI, W&B, MLflow, additional OpenEnv tasks, and additional provider cases can be
stable when their own evidence is present or preview otherwise. The release cannot
downgrade all three differentiating external boundaries and still call itself 1.0.

## Schema and compatibility policy

Many artifact kinds currently identify themselves with `v0alpha1`, and schema
names participate in artifact digests. Renaming those schemas in place would
silently change artifact identity. The minimal compatible 1.0 policy is:

- Existing `v0alpha1` wire formats become **legacy-frozen**. Arena 1.x reads them
  for the entire 1.x line and does not reinterpret their bytes.
- Existing writers may continue emitting those identity-preserving schemas in 1.x.
  “Alpha” in a historical schema name does not mean mutable after 1.0.
- New schemas use stable version names and require an explicit reader/writer
  compatibility rule before merge.
- One schema registry records kind, version, status (`stable`,
  `legacy-frozen`, `preview`), reader range, writer range, and migration behavior.
- Golden artifacts from 0.2, 0.3, and 0.5 are installed as compatibility fixtures.
  A clean 1.0 wheel must inspect and verify them.
- A migration that changes identity creates a new artifact and records the source
  digest. It never mutates the old artifact in place.

This closes the compatibility promise without breaking the artifacts that proved
the earlier milestones.

### Identity model

The v1 schemas separate **semantic intent** from **execution binding**. Historical
`v0alpha1` readers and digests remain byte-for-byte frozen; an explicit migration
creates a new v1 artifact linked to the legacy digest.

| Artifact family | Exact semantic identity | Operational evidence excluded from that identity |
|---|---|---|
| Policy | schema/canonicalization version, model contract, roles/spaces, payload digests, reference-suite digest | local path, store URI, signature, download time |
| Task intent | environment/game ID and revision, role/space/protocol semantics, interaction family | endpoint, container ID, credential, retry/timeout |
| Match intent | task-intent digest, policy digests/roles, seeds, action semantics, declared missingness/failure policy | worker count, host, start time, process ID |
| Trajectory/result | canonical observations/actions/rewards/termination plus exact source identities | log paths, timing, platform diagnostics |
| Evaluation intent | suite/cells/metrics, semantic provider configuration, source digests, tolerance/missingness policy | interpreter path, endpoint, process settings, timeout implementation |
| Evaluation run | evaluation-intent digest plus binding digest, attempts, complete/incomplete/failed state | presentation-only log location |
| Dataset/training | source episode digests, split algorithm/seed, recipe/trainer state required for exact resume | workspace paths, scheduling, telemetry endpoints |
| Mirror/store | artifact descriptor and blob digests | mutable source ref after it has resolved, credentials, transfer timing |
| Qualification/evidence | subject digest, immutable backend/runtime revision, result and mode | expiring log URL; logs are bundled or content-digested |

New schemas name their canonicalization algorithm and declare unknown-field and
extension behavior. Unknown identity-bearing fields are never silently ignored.
JSON/YAML parsing is bounded and strict: duplicate keys, non-finite numbers,
excessive aliases/depth/size, malformed digests, and ambiguous portable paths are
rejected.

Native and OpenEnv execution share a task-intent digest when and only when their
verified semantic contract is the same. They have different binding and run
digests. Likewise, native and Gimitest evaluations can share an evaluation-intent
digest while recording distinct provider bindings and result evidence.

## 1.x compatibility promise

The stable compatibility surface is deliberately small:

- the top-level Python imports exported by `arena.__all__`: `Task`, `Policy`,
  `Match`, `Population`, `Evaluation`, and `check`;
- documented CLI command names, required arguments, exit categories, and
  versioned `--json` envelopes;
- stable and legacy-frozen manifest schemas in the schema registry;
- release-evidence, qualification, attestation, and diagnostic codes;
- registry lookup semantics and the documented protocol for third-party entries.

Private modules, undocumented flags, preview registry entries, exact prose, and
human-readable error wording are not stable API. Additive fields are allowed only
where the relevant schema declares them forward-compatible. A removal or
meaning-changing change to the stable surface waits for 2.0. Deprecations remain
functional for at least two minor releases and six months, whichever is longer,
and emit both a human warning and a machine-readable replacement field.

Contract snapshots run the oldest supported 1.x client fixtures against the new
reader and the new client against historical artifacts. The versioned release
documentation is packaged and linked from each release so a later branch edit
cannot rewrite the promise of an older tag.

The global CLI grammar is frozen:

- `--version`, `--json`, and `--debug` work before or after the subcommand;
- stdout is the only JSON stream; progress and warnings use stderr;
- success is `arena.cli-result/v1` with `ok`, `command`, `data`, and `warnings`;
- failure is `arena.diagnostic/v1` with `ok: false`, `code`, `category`,
  `message`, `cause`, `repair`, `docs_url`, redacted `context`, and `command`;
- argparse/usage errors also honor JSON mode;
- exit codes are 0 success, 2 usage, 3 schema/compatibility, 4
  integrity/authenticity, 5 external unavailable/timeout, 6
  incomplete/cancelled, and 70 unexpected internal fault;
- tracebacks appear only with `--debug` and remain redacted.

CLI help and JSON golden snapshots are compatibility fixtures.

Registry discovery is lazy and versioned. Installed entry points are loaded only
when their kind is referenced; built-in name collisions fail, registration faults
identify the plugin distribution, and uninstalling a plugin cannot break core
startup. A tiny out-of-tree plugin wheel is the executable contract test.

### Install and discovery profiles

| Install | Provides |
|---|---|
| `arena` | Inspect, identity, manifests, local artifacts, and `file://` |
| `arena[quickstart]` | Exact packaged handoff demo and its in-process reference runtime |
| `arena[openenv]`, `arena[openspiel]`, `arena[hf]` | One named capability each |
| Separate Gimitest worker environment | Resolver-isolated provider runtime |
| OCI extra plus ORAS executable | OCI client boundary |

The existing `all` extra is documented as “all compatible in-process
capabilities,” not every external integration. It emits deprecation guidance in
1.x toward named profiles and can be removed only under the compatibility policy.
Every missing dependency diagnostic names the exact extra, executable, or isolated
worker command.

`arena doctor [--capability NAME] [--json]` reports stable/preview/unsupported or
locally unqualified status, the current OS/architecture/Python row, installed and
missing dependencies with exact repair, required executables/interpreters,
live-versus-simulated evidence timestamp/expiry, and whether credentials will be
needed. It performs no authentication. External commands run this preflight
before touching credentials.

`arena demo handoff --out DIR` is a thin orchestration of existing primitives using
a packaged, versioned fixture. It works source-free and network-free after install,
prints the source/restored policy digests, verification result,
evaluation-intent digest, capability labels, and next real-user command, and is
safe to interrupt and rerun.

The published first-value flow is three commands:

```bash
python -m pip install 'arena[quickstart]==1.0.0'
arena demo handoff --out ./arena-demo
arena inspect ./arena-demo/restored-policy.arena
```

A prepared platform means a claimed OS/architecture with a supported Python
already installed, a fresh virtual environment, a writable working directory, and
network access only for the timed install. Report cold install time,
installed-to-first-verified-artifact time, and total local-demo time separately.
The five-minute gate applies from completed installation to the verified artifact;
the complete local demo must also finish within five minutes.

The v1 plugin authoring contract uses entry-point group `arena.plugins.v1`. An entry
point is a zero-argument `register() -> None` callable; its distribution declares
`arena>=1,<2`, and Arena obtains distribution name/version from package metadata.
Registries reject collisions. The canonical `arena-example-store` wheel implements
an inert local test scheme and documents install, `arena doctor`, `arena store
qualify`, use, and uninstall. Passing local qualification yields
`locally-qualified` local evidence; a plugin cannot label itself release-stable.

## Evidence architecture

Release evidence becomes a product artifact rather than a prose checklist:

```text
source commit + support matrix + schema registry
                         |
                         v
                  release candidate
                 /        |        \
          platform CI  live quals  human handoff
                 \        |        /
                  signed evidence records
                         |
                         v
              arena.release-evidence/v1
                         |
                  release verify
                         |
              tag + wheels + sdist + SBOM
```

The repository contains the evidence schema and an unbound template, not the
completed index. The completed `evidence-index.json` is an immutable release asset;
putting it in the commit whose digest it records would create a self-reference.
`docs/qualifications/current.json` is a separate, append-only current-status
ledger for qualifications that later expire, fail, or recover. A status change
never rewrites release history. If it changes what newly installed Arena promises,
it ships in a patch release as well as the current ledger.

Each gate record
contains:

- gate ID and capability label;
- commit and tag;
- platform, Python version, dependency set, and execution mode;
- exact command or workflow identity;
- result artifact digest and timestamp;
- freshness deadline for external qualifications;
- pass, downgrade, or waiver status and owner;
- links to logs, attestations, and public release artifacts.

The release index also records its signer, public-key fingerprint, signature
algorithm, detached-signature digest/location, and trust policy. Individual
reports are content-digested into that signed index; they do not each need a
separate signature. Package-index provenance proves where the distribution was
built and published, while the Arena signature binds the release decision and its
evidence. These are related but distinct claims. Release identity relies on the
signed repository tag and hosted package provenance. A detached Arena Ed25519
signature asserts publisher identity only when the verifier receives the public
key through an independent trust channel.

Historical verification is explicitly offline:

```bash
arena release verify evidence-index.json \
  --signature evidence-index.sig \
  --key arena-release.pub \
  --at-release
```

Current status requires an explicit ledger path or URL:

```bash
arena release verify evidence-index.json \
  --signature evidence-index.sig \
  --key arena-release.pub \
  --current-ledger current.json
```

Release verification validates the schema, commit/tag binding,
required gate coverage, linked local artifact digests, expiry, and allowed
downgrades as of publication. Current mode also applies the supplied qualification
ledger. Old releases remain historically verifiable after live evidence expires.
Neither mode pretends to re-run a remote service, and ledger unavailability is
distinct from release invalidity.

## Reliability contracts

### Transactional publication

Every user-visible producer follows the same protocol:

```text
validate inputs -> write isolated staging area -> fsync/close
      -> verify staged identity -> atomic publish -> verify final identity
```

On interruption, the final path is absent or the prior valid artifact remains.
Temporary state is cleaned on retry. Every producer is inventoried and assigned
one publication mode:

| Output | Publication mode |
|---|---|
| Immutable artifact directory | Same-parent staging, full verification, create-only atomic rename, parent-directory sync |
| Immutable content-addressed object | Unique temporary file, hash, file sync, create-only publish, existing-object re-verification |
| Mutable ref or descriptor | Complete temporary file, file sync, atomic replace, parent-directory sync |
| Diagnostic partial state | Visibly marked incomplete/failed and never accepted as a successful artifact |

The inventory includes match/AEC/dynamic runs, evaluation runs/bundles/reports,
population output, dataset/training, task import, mirror pull, store blobs/refs,
qualifications, local refs, and key generation. The shared helper reuses the
staging pattern already present in dataset materialization and training.

External stores publish blobs idempotently and the descriptor last. Orphan
content-addressed blobs are safe and collectable; a descriptor must never point
at missing or unverified content. Every downloaded blob is content-hash verified
unconditionally. `pull --verify` adds artifact-structure and authenticity checks;
it never controls whether known-hash bytes are checked.

Mutable remote names are resolved once. Hugging Face descriptor and blobs are
fetched from the same immutable commit; OCI content is fetched by manifest digest.
A branch or tag moving mid-operation either has no effect on the pinned fetch or
causes an explicit abort.

### Diagnostics

All expected user failures derive from one structured diagnostic contract:

- stable error code and category;
- what failed, likely cause, and one concrete repair;
- safe context fields with credentials and tokens redacted;
- human-readable output by default;
- the same information in a versioned JSON envelope under `--json`;
- traceback only under `--debug`;
- exit classes for usage, compatibility, integrity, external availability, and
  internal fault.

Unexpected faults remain faults; Arena must not flatten them into misleading
“invalid input” messages.

## Error and rescue registry

| Failure category | Stable signal | Rescue behavior |
|---|---|---|
| Usage or copied placeholder | Exit 2 / `USAGE_*` | Point to valid syntax and matching versioned docs |
| Missing extra/executable/interpreter | Exit 3 / `CAPABILITY_MISSING` | Name exact install profile or isolated-worker command; run no credentialed action |
| Schema/API incompatibility | Exit 3 / `COMPAT_*` | Name received/supported versions and migration or downgrade path |
| Content corruption | Exit 4 / `INTEGRITY_*` | Preserve prior valid output, quarantine/remove staging, identify first bad object |
| Signature/trust failure | Exit 4 / `AUTHENTICITY_*` | Distinguish wrong bytes from missing/incorrect independent trust anchor |
| External auth/rate/service failure | Exit 5 / `EXTERNAL_*` | Redact secrets, preserve immutable resolved revision, give bounded retry or credential repair |
| Timeout/cancellation/incomplete run | Exit 6 / `EXECUTION_*` | Kill supervised descendants, retain incomplete attempt ledger, publish no valid result |
| Plugin load/collision failure | Exit 3 / `PLUGIN_*` | Identify distribution/version/name, isolate failure, keep offline core operational |
| Unexpected internal fault | Exit 70 / `INTERNAL` | Redacted incident ID/context; optional debug trace; no false user blame |

Every rescue path is exercised in human and JSON mode. Help links are supplementary;
the local diagnostic contains a complete repair when documentation is unreachable.

### Budget and cancellation

Timeout, process, file-count, archive-size, response-size, and concurrency budgets
are enforced, recorded in evidence, and inherited through composed workflows.
Stable hard budgets use a supervised subprocess per evaluation cell or episode;
the supervisor terminates the entire descendant process group and bounds its
request, response, stdout, and stderr. In-process threads remain a cooperative,
trusted fast path and do not claim hard cancellation.

`reset`, policy action, `step`, and `close` each receive bounded execution.
Retries restart a whole episode and append an attempt record. Arena never retries an
ambiguously delivered external step inside the same episode. Partial evaluation
output is diagnostic state, never a valid completed evaluation artifact.

Evaluation states are `complete`, `incomplete`, and `failed`. Every report records
attempted/completed/failed denominators. Missing-data policy and its threshold are
semantic, identity-bearing inputs; a metric cannot silently average only the
successful seeds. A semantic result digest excludes scheduling and worker count,
while the operational run digest records attempts and bindings.

### Exact identity versus semantic reproduction

Canonical manifests, payload bytes, policy digests, suite definitions, and
lineage links must match exactly when the same artifact is handed off. Runtime
reports may include platform, timestamps, and operational evidence outside that
semantic identity. Cross-runtime numerical results reproduce within the declared
tolerance and seed contract; they are not required to have the same report-file
digest. Equivalence reports identify both the exact input identities and the first
out-of-tolerance field.

## Known hazards to close

| ID | Hazard found in 0.5 | 1.0 response |
|---|---|---|
| H-01 | OpenEnv schema verification is process-cached, so a later client can miss server drift | Verify the schema on every new client session; cache only immutable parsing |
| H-02 | OpenEnv step responses do not fully validate exact agent keys, types, or finite values | Central typed response validator with protocol-error diagnostics |
| H-03 | OpenEnv close failures are swallowed | Preserve primary result but emit a structured cleanup diagnostic |
| H-04 | Mirror restore writes directly into the final output | Stage, verify, and atomically rename; clean failed staging |
| H-05 | Evaluation can leave a partial run root when one worker fails or hangs | Supervised-process execution, transactional run publication, explicit state and failure ledger |
| H-06 | Evaluation budgets influence identity but are not consistently enforced | Define and enforce inherited budgets at the execution boundary |
| H-07 | Gimitest checks are narrower than its subprocess trust boundary | Versioned request/response envelope, size cap, digest correlation, stderr cap/redaction, process-group cleanup |
| H-08 | OCI extraction checks paths and link types but not decompression/file-count bombs | Enforce archive byte, expanded byte, and member-count budgets |
| H-09 | CLI error text is human-only and unstable | Add structured diagnostic codes and JSON output |
| H-10 | Versioned docs contain hard-coded older wheel names | Generate/version-check release snippets in CI |
| H-11 | No public publishing or release provenance workflow exists | Trusted publishing, release assets, hashes, SBOM, provenance, and post-publish install verification |
| H-12 | Live and human evidence templates exist but are not populated | Make evidence-index coverage a tag blocker |
| H-13 | Semantic artifacts include interpreter paths, endpoints, and other bindings | Add v1 intent/binding split and migrate with source lineage |
| H-14 | Entry-point registration exists but is not invoked by normal CLI discovery | Freeze lazy discovery/collision semantics and qualify an out-of-tree plugin wheel |
| H-15 | Parsers/canonical JSON accept ambiguous keys or non-finite values and digest parsing is loose | Strict bounded parsing, named canonicalization, exact digest grammar, golden vectors |
| H-16 | Gimitest's present no-op base path and dependency conflict do not prove provider value | Early resolver/non-no-op feasibility gate and provider-native assertion evidence |

## Delivery sequence

### Phase 0 — De-risk external prerequisites

Before broad implementation:

- configure or assign owners for the Git remote, PyPI project and Trusted
  Publisher, release signing identity, Hugging Face test repository, separate
  OpenEnv service/image, macOS arm64 Python 3.13 runner, and independent users;
- prove a resolver-clean Gimitest worker environment with all required runtime
  dependencies;
- run one deterministic non-no-op Gimitest scenario and capture native assertions
  and perturbation evidence;
- freeze the capability × platform × Python matrix and the minimum external floor;
- preflight package-index name ownership and the availability of the exact
  capability extras named in user instructions.

Gimitest is stable only if the worker is reproducible and its provider-native
evidence proves behavior beyond the no-op base hook. If upstream cannot satisfy
that with an isolated lock/constraint set or a narrowly owned compatibility worker,
Gimitest is preview and `v1.0.0` remains blocked until the stable Gimitest claim is
formally replaced by RFC and a genuinely external provider is qualified. Simulated
lineage is not a substitute. This go/no-go is first because it can change the
release schedule, though not the core architecture.

### Phase 1 — Freeze the promise

Deliver:

- machine-readable support matrix and schema registry;
- artifact-family identity projections and v1 intent/binding schemas;
- stable/preview/unsupported terminology in CLI and docs;
- golden 0.2/0.3/0.5 compatibility fixtures;
- authentic fixture provenance: original tag/commit, generating command, and
  original digest, never fixtures synthesized by current code;
- `arena.release-evidence/v1` schema and `release verify`;
- the frozen public CLI/SDK/JSON surface and deprecation policy;
- the packaged `arena[quickstart]` fixture, `arena demo handoff`, and `arena doctor`;
- lazy out-of-tree registry discovery and its clean plugin-wheel contract;
- strict bounded parsers, digest grammar, canonicalization vectors, and portable
  case/Unicode path-collision policy;
- one package-version source, with runtime version read from installed metadata;
- release-gate ownership and evidence freshness policy.

Acceptance:

- Every README capability maps to one support-matrix row.
- A clean wheel reads all promised historical fixtures.
- Each historical fixture is traceable to its original release output.
- Changing or omitting a required claim causes evidence verification to fail.
- No schema rename changes an existing digest.
- From an installed wheel, the three-command local handoff completes without the
  checkout or network and `doctor` predicts every required dependency repair.

This phase goes first because every later test result must attach to a frozen claim.

### Phase 2 — Make failure safe and actionable

Deliver:

- shared atomic-publication helper and adoption by mirror, evaluation, and
  every inventoried producer;
- structured diagnostics and exit classes;
- centralized budget/cancellation context;
- supervised subprocess executor for hard-budget stable runs, with cooperative
  in-process execution explicitly weaker;
- OpenEnv per-session pin and typed response validation;
- hardened Gimitest envelope and OCI archive budgets.

Acceptance:

- Fault injection at each publication step leaves either the old valid artifact or
  no final artifact.
- Every expected failure in the messy-test plan has a stable code, safe JSON, and
  a repair.
- No timed-out subprocess, thread, temporary directory, or partial descriptor
  survives a completed command.

### Phase 3 — Prove installation and platform support

Deliver:

- CI matrix for the claimed platform/Python combinations;
- build-once wheel and sdist artifacts;
- network-disabled install and handoff from a local wheelhouse;

### Phase 8 — Publish, verify, and rehearse recovery

Release sequence:

```text
publish rcN artifacts -> clean-machine smoke -> seven-day bake
  -> freeze final commit (version-only change from baked RC)
  -> build final-version artifacts once -> run exact-artifact mandatory gates
  -> upload exact bytes to TestPyPI -> clean install
  -> generate and sign evidence asset -> signed tag binds commit + evidence digest
  -> upload the same wheel/sdist bytes to PyPI -> post-publish verify
```

Rollback sequence:

```text
detect bad release -> stop promotion -> preserve evidence
  -> mark affected claim/release -> yank package if consumer-dangerous
  -> publish a patch -> re-run affected and transitive gates
```

PyPI releases are not deleted or overwritten. A broken distribution is yanked when
necessary and replaced by a patch. External capability evidence is immutable; a
revoked qualification produces a new status record and support-matrix update.

## Proof journeys

The release candidate must execute these value demonstrations from a clean install:

1. **Producer → consumer policy handoff:** producer builds and signs a policy,
   pushes it to a stable store, consumer pulls with verification, preserves the
   exact evaluation-intent digest, and reproduces numerical results within the
   declared tolerance.
2. **Native → OpenEnv semantic equivalence:** one policy/eval definition runs
   natively and through the separate service; the trace verifier proves equality or
   pinpoints divergence.
3. **Evaluation provider swap:** built-in and Gimitest providers consume the same
   evaluation-intent identity and emit lineage-linked, provider-native reports
   under distinct execution bindings without changing the source artifact.
4. **Resume after interruption:** a trainer is terminated after a published
   checkpoint, resumes exactly, and produces the same declared result as the
   uninterrupted reference.
5. **Dynamic lifecycle replay:** an agent ID leaves and re-enters repeatedly; segment
   history and role assignment reproduce without recurrent-state contamination.
6. **Failure recovery:** an interrupted pull or evaluation leaves no valid-looking
   partial result; retry succeeds with the same final identity.
7. **Third-party producer:** clone CleanRL at commit
   `fe8d8a03c41a7ef5b523e2e354bd01c363e786bb`, train its CartPole DQN in an
   isolated environment, export the learned categorical Q-policy through Arena's
   existing BYO-module surface with a source-captured reference suite, remove the
   CleanRL checkout, and verify/load the artifact as a consumer. This tests a real
   public-repository producer without adding CartPole task support to Arena core.

The exact commands, fixtures, expected digests, and failure variants are in
`docs/1.0-test-plan.md`.
